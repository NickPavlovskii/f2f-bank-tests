## BUG-01 | После Logout кнопка «Назад» открывает закешированную главную

| | |
|---|---|
| **Приоритет** | Высокий |
| **Область** | Авторизация / безопасность (bfcache) |
| **Окружение** | Chromium, `http://localhost` |
| **Тест** | TC-LOGOUT-02 (падает: ожидался `/login`, факт `http://localhost/`) |

### Шаги
1. Войти в систему.
2. Открыть главную `/`.
3. Нажать Logout в шапке → оказались на `/login`.
4. Нажать Back в браузере.

### Фактически
URL становится `http://localhost/` — отображается закешированная авторизованная страница (bfcache).

### Ожидалось
Пользователь не должен видеть защищённый экран. Нужен редирект на `/login` либо пустой/гостевой UI без данных сессии.

### Риск
На банковском UI это выглядит как восстановление сессии после выхода. Даже если cookie уже очищен, кратковременный показ личного экрана недопустим.

### Заметка
Logout на клиенте чистит cookie и `profile` локально, но **не вызывает** `POST/GET /api/auth/logout`. Страница не помечается как `Cache-Control: no-store` для bfcache.

## GAP-SEC-01 | Нет rate limiting / lockout на `/api/auth/login`

| | |
|---|---|
| **Приоритет** | Средний (security finding) |
| **Область** | Авторизация / brute-force |
| **Окружение** | Chromium, `http://localhost` |
| **Тест** | TC-SEC-02 (проходит: фиксирует gap, не проверяет соответствие) |

### Шаги
1. Зарегистрировать пользователя через API.
2. Отправить 10 подряд `POST /api/auth/login` с верным email и неверным паролем.

### Фактически
Все ответы **401 Unauthorized**. Нет **429 Too Many Requests**, задержки и блокировки аккаунта.

### Ожидалось (для банков желательно)
Rate limiting по IP/email, временная блокировка или экспоненциальная задержка после серии неудачных попыток.

### Риск
Brute-force перебор паролей без ограничений.

### Заметка
`expect(statuses).not.toContain(429)` — **documenting assertion**. Когда защита появится, тест упадёт как сигнал обновить TC-SEC-02 на позитивную проверку (ожидать 429 после N попыток).

## BUG-02 | Cookie `access_token` без флага HttpOnly

| | |
|---|---|
| **Приоритет** | Высокий |
| **Область** | Авторизация / безопасность сессии |
| **Окружение** | Chromium, `http://localhost` |
| **Тест** | TC-SEC-01 (падает: `httpOnly` = false) |

### Шаги
1. Зарегистрировать пользователя.
2. Выполнить успешный login.
3. Проверить атрибуты cookie `access_token` в браузере.

### Фактически
Cookie устанавливается, но **`httpOnly: false`** — доступна из JavaScript (`document.cookie`).

### Ожидалось
`HttpOnly=true` и `SameSite=Lax` или `Strict`, чтобы снизить риск кражи сессии при XSS.

### Риск
При любой XSS-уязвимости злоумышленник может прочитать JWT из cookie и украсть сессию.

### Заметка
`auth_controller.login_user` вызывает `response.set_cookie(name, token)` без `httponly=True`. AuthX по умолчанию не выставляет HttpOnly при таком вызове.
